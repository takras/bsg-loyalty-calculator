# iOS build

The native iOS app is built on a GitHub-hosted macOS runner (`.github/workflows/ios.yml`, adapted from
legion-helper), not on a local machine. Everything up to `xcodebuild` also runs on Windows, so the
web/sync half can be checked locally with `npm run build && npx cap sync ios`.

## Running a build

Actions → **Build iOS app** → Run workflow, and pick a target:

| Target            | Produces                               | Runs on                     |
| ----------------- | -------------------------------------- | --------------------------- |
| `device-unsigned` | `BSGCompanion-<version>-unsigned.ipa`  | Nothing – proves it builds  |
| `simulator`       | `BSGCompanion-simulator.zip`           | The iOS Simulator, on a Mac |
| `testflight`      | Signed `.ipa`, uploaded to TestFlight  | Any device via TestFlight   |

All land in the run's artifacts; `testflight` also needs the secrets below.

**Versions** come from `package.json`: marketing version `1.2.3`, build number `10203` – the same scheme
as the Android `versionCode` (see `android/app/build.gradle`). Bump with `npm version patch|minor|major`
before a release. `build_number` is an optional input: set it when re-uploading the same marketing
version, because App Store Connect rejects a build number it has already accepted.

Manual trigger only, on purpose: on a private repo macOS minutes bill at a **10× multiplier**, so a push
trigger would drain the monthly allowance fast. (On a public repo they are free.) The job is capped at 45
minutes.

## Runner and SDK

The job runs on `macos-26`: App Store Connect rejects uploads built against an SDK older than **iOS 26**,
and older images only ship older Xcode versions – the archive would build and sign, then be refused at
upload. The Xcode version is not pinned, so the image default follows Apple's requirements; the build
logs the Xcode and SDK version early.

## What "unsigned" means

`device-unsigned` sets `CODE_SIGNING_ALLOWED=NO`, so no Apple account is needed. It proves the app
compiles, links and bundles, and the `.ipa` can be unzipped and inspected – but **iOS will not install
it**. The `testflight` target produces a properly signed build and needs the Apple Developer Program.

## Signing setup

No certificate is ever exported from a Mac. `xcodebuild` gets `-allowProvisioningUpdates` together with
App Store Connect API credentials, and Xcode creates and downloads the signing certificate and
provisioning profile itself.

Repository secrets (Settings → Secrets and variables → Actions). The same Apple account and API key as
legion-helper can be reused:

| Secret                          | Where it comes from                       |
| ------------------------------- | ----------------------------------------- |
| `APPLE_TEAM_ID`                 | developer.apple.com → Membership details  |
| `APP_STORE_CONNECT_KEY_ID`      | The API key's Key ID                      |
| `APP_STORE_CONNECT_ISSUER_ID`   | The API key's Issuer ID                   |
| `APP_STORE_CONNECT_PRIVATE_KEY` | The whole `.p8`, BEGIN/END lines included |

The key is a **Team key with the Admin role** (App Store Connect → Users and Access → Integrations →
App Store Connect API); App Manager cannot manage certificates.

An **app record with bundle id `net.takras.bsg`** must exist in App Store Connect before the first upload
(Apps → + → New App). `-allowProvisioningUpdates` registers the bundle id in the developer portal, but it
does not create that record.

Every signed run creates a certificate on the throwaway runner and leaves it on the Apple account. Apple
caps how many an account holds; at the cap the archive fails with "Your account has reached the maximum
number of certificates". Run the workflow once with **revoke_old_certificates** ticked: it revokes only
certificates named "Created via API", never hand-made ones. The cap is per account, so runs from
legion-helper and this app count together. `node scripts/revoke-api-certificates.mjs --dry-run` lists
what would go.

## How the pieces fit

- **Plugins** – Capacitor 8 uses Swift Package Manager, not CocoaPods: no Podfile, no `.xcworkspace`.
  `ios/App/CapApp-SPM/Package.swift` points at `node_modules`, so `npm ci` runs before `xcodebuild`.
- **Scheme** – `App.xcscheme` is committed under `App.xcodeproj/xcshareddata/xcschemes/`; CI never opens
  Xcode, so it would not exist otherwise.
- **Export compliance** – `Info.plist` sets `ITSAppUsesNonExemptEncryption = false` (the app uses no
  encryption beyond the system's HTTPS), so builds don't wait on the compliance question in TestFlight.
- **Icons and splash** – generated by `npm run icons` into `ios/App/App/Assets.xcassets` (committed).
- **Safe areas** – `viewport-fit=cover` plus `env(safe-area-inset-*)` in `src/styles.css`; on iOS the
  web view reports the status bar and home indicator through `env()`.
- **iPad** – the project targets iPhone and iPad (`TARGETED_DEVICE_FAMILY = 1,2`). An App Store release
  (not TestFlight) then also needs iPad screenshots; set it to iPhone only in the project if that's not
  wanted.
